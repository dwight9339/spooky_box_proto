# Spooky Probe / Spooky Trace
## Implementation Plan for a Raspberry Pi Pico Debug + Telemetry Probe

**Status:** Proposed development plan  
**Target probe:** Raspberry Pi Pico (RP2040), initially using a fork of Raspberry Pi `debugprobe`  
**Primary target:** Spooky Box prototype on STM32H745/H755-class dual-core MCU  
**Primary target board during bring-up:** NUCLEO-H755ZI-Q  
**Audience:** Human developer + Codex/other coding agents

---

## 1. Purpose

Spooky Probe is intended to evolve the existing Pico-based CMSIS-DAP + UART debug probe into a purpose-built development instrument for Spooky Box.

The central problem it should solve is not merely "how do I print logs?" It should answer:

> What was happening on both STM32 cores, and in the important real-time subsystems, immediately before and during a timing-sensitive failure?

Spooky Box deliberately divides responsibilities between two cores:

- **Cortex-M7:** audio capture, DSP, recording-critical work, storage coordination, radio/scan behavior, authoritative state.
- **Cortex-M4:** UI/service work, controls, display/matrix rendering, housekeeping, diagnostics, and UART logging.

This split protects the M7's real-time work, but it also creates bugs that can be temporal and cross-domain: an SD write, UI transfer, inter-core event burst, or DSP frame may occasionally overlap in a harmful way. Ordinary serial logs are often insufficient to reconstruct those interactions.

Spooky Probe should provide three complementary views of the target:

1. **SWD / CMSIS-DAP** - inspect and control processor state.
2. **UART console** - human-readable logs and diagnostics.
3. **Spooky Trace** - independent, timestamped hardware-event capture and structured telemetry.

The intended result is a single USB-connected probe that remains useful throughout prototype development, even if a commercial ST-Link is later added to the toolchain.

## 2. Design Principles

### 2.1 Preserve debugging first

Spooky Trace must never make CMSIS-DAP materially less reliable.

If resource conflicts arise, the priority order is:

1. CMSIS-DAP / SWD correctness
2. Hardware trace capture correctness
3. UART bridge reliability
4. Trace streaming throughput
5. Convenience features

A trace overflow is acceptable. A broken debugger is not.

### 2.2 Observe externally where possible

The probe should obtain important timing information through dedicated target GPIO signals observed by the Pico, rather than relying entirely on software timestamps generated by the STM32.

This gives the trace system an independent timebase and keeps it useful when one STM32 core is overloaded, blocked, or faulting.

### 2.3 Instrumentation must be cheap

Instrumentation added to timing-sensitive M7 code must be extremely low overhead and deterministic.

For hot paths, prefer direct GPIO `BSRR` writes or compact binary events. Avoid printf-style formatting, heap allocation, blocking locks, and synchronous UART transmission.

### 2.4 Best-effort diagnostics must never block real-time work

If telemetry or logging buffers fill, drop trace/log data and increment a counter. Never block M7 DSP/audio execution waiting for a diagnostic consumer.

### 2.5 Start simple, then earn complexity

Do not begin with a custom GUI, exotic USB class, elaborate compression scheme, or generalized logic analyzer.

The first useful version is:

- stock CMSIS-DAP still works,
- stock UART bridge still works,
- one trace GPIO can be timestamped,
- a host script can display or save those events.

Everything else should be added incrementally.

## 3. Relationship to the Spooky Box Architecture

The current Spooky Box architecture emphasizes isolation between recording-critical and presentation workloads. The default split places high-rate audio/DSP and recording responsibilities on M7 and UI/service/diagnostics work on M4.

Spooky Probe complements that architecture in two ways:

1. **M4 remains the owner of the normal debug UART.** Both cores may log through a shared nonblocking logging service, but the physical UART peripheral is owned and serviced by M4.
2. **Spooky Trace remains external to both cores.** Important timing windows are represented on dedicated GPIOs and captured by the Pico independently.

This means normal debugging can look like:

```text
M7 ---- shared log queue ----> M4 ---- UART ----> Pico ----> terminal
 |                            |
 +---- TRACE GPIOs -----------+-----------> Pico ----> Spooky Trace

PC ---- CMSIS-DAP ----> Pico ---- SWD ----> STM32H755
```

The logging path explains software intent and state. The trace GPIO path measures timing. SWD provides deep inspection when necessary.

## 4. Scope

### 4.1 Phase-one scope

Spooky Probe v0.x should support:

- Existing Raspberry Pi `debugprobe` CMSIS-DAP functionality.
- Existing target UART-to-USB CDC bridge.
- 1-4 adjacent trace GPIO inputs.
- Edge/state-change capture.
- Pico-side timestamping.
- Buffered USB streaming of trace records.
- A host-side Python capture/decoder utility.
- Trigger input and circular pre-trigger history in a later v0.x milestone.

### 4.2 Later scope

Potential later features:

- Structured STM32 binary telemetry merged with hardware trace.
- Multiple trace configurations/profiles.
- Trigger conditions beyond a single input edge.
- Vendor-specific USB bulk transport.
- Timeline GUI.
- Export to an existing trace-viewer format.
- Event bus/strobe encoding for many logical events.
- Host commands to arm/freeze/configure captures.
- Postmortem/crash-record collection.

### 4.3 Explicit non-goals for initial versions

Do not initially attempt to:

- Replace a full logic analyzer.
- Decode arbitrary SPI/I2C/SAI/SDMMC traffic.
- Implement general-purpose oscilloscope functionality.
- Reimplement SWD.
- Replace OpenOCD/GDB.
- Build a production-grade desktop GUI.
- Make the target dependent on Spooky Probe to run normally.

The Spooky Box must operate correctly with the probe disconnected.

## 5. Baseline: Fork Raspberry Pi `debugprobe`

Use Raspberry Pi's official `debugprobe` firmware as the starting point.

Official repository:

- https://github.com/raspberrypi/debugprobe

The stock project already provides the two most valuable baseline services:

- CMSIS-DAP over USB for SWD debugging.
- USB CDC UART bridging.

The fork should be kept as close to upstream as practical. Avoid unnecessary refactors of the existing DAP or UART code during early milestones.

### Recommended branch strategy

```text
upstream/master          Raspberry Pi upstream
main                     known-good Spooky Probe integration branch
feature/trace-minimal    first GPIO capture experiment
feature/trace-pio        PIO capture
feature/trace-dma        DMA buffering
feature/trace-trigger    pre/post-trigger capture
feature/telemetry        structured target telemetry
```

Periodically merge or rebase upstream changes only after the current Spooky branch has passing smoke tests.

## 6. Proposed Probe Hardware Pin Allocation

Current/debugprobe-oriented pins should remain untouched where possible.

A provisional Pico mapping is:

```text
GP1   target NRST
GP2   SWCLK
GP3   SWDIO
GP4   UART TX from Pico -> STM32 RX
GP5   UART RX to Pico   <- STM32 TX

GP10  TRACE0 / M7_AUDIO_ACTIVE
GP11  TRACE1 / M7_STORAGE_ACTIVE
GP12  TRACE2 / M4_UI_ACTIVE
GP13  TRACE3 / TRACE_TRIGGER

future:
GP14  TRACE4 / IPC_ACTIVITY
GP15  TRACE5 / RADIO_ACTIVITY or spare
```

The trace pins should be contiguous when practical because RP2040 PIO can read a contiguous group efficiently.

### Electrical assumptions

- Target trace signals are 3.3 V logic.
- Pico and STM32 share ground.
- Trace inputs are target-to-probe only.
- The Pico must not accidentally drive trace inputs.
- Target-side optional series resistors or small protection components may be considered on future custom hardware, but the initial Nucleo setup can use direct 3.3 V GPIO wiring.

### Future custom connector

A future Spooky Box PCB could expose a single development header carrying:

```text
VTREF
GND
SWDIO
SWCLK
NRST
SWO (optional)
UART_TX
UART_RX
TRACE0
TRACE1
TRACE2
TRIGGER
```

Additional trace/event pins may be exposed on a second header if necessary.

## 7. STM32 Instrumentation Model

### 7.1 Dedicated timing pins

The first useful assignment is:

- `TRACE0`: M7 audio/DSP critical interval.
- `TRACE1`: M7 storage/SD critical interval.
- `TRACE2`: M4 UI/display rendering interval.
- `TRACE3`: fault/trigger pulse.

The exact semantics should remain stable within a capture profile so that host tools can label them consistently.

### 7.2 Low-overhead macros

For timing-sensitive paths, instrumentation should compile to direct GPIO writes.

Example conceptual API:

```c
TRACE_AUDIO_BEGIN();
process_audio_block();
TRACE_AUDIO_END();
```

Implementation pattern:

```c
#define TRACE_AUDIO_BEGIN() (TRACE_GPIO->BSRR = TRACE_AUDIO_PIN)
#define TRACE_AUDIO_END()   (TRACE_GPIO->BSRR = ((uint32_t)TRACE_AUDIO_PIN << 16U))
```

The final implementation should use the actual STM32 HAL/device definitions and verify that these macros are safe for the selected port/pin.

### 7.3 Compile-time disabling

Instrumentation must be removable:

```c
#if SPOOKY_TRACE_ENABLE
  #define TRACE_AUDIO_BEGIN() ...
#else
  #define TRACE_AUDIO_BEGIN() ((void)0)
#endif
```

Release firmware should be able to compile with all trace macros becoming no-ops.

### 7.4 Avoid printf in hot paths

Do not place expensive string formatting inside audio DMA callbacks or similar hard timing paths.

For high-rate diagnostic data, prefer either:

- GPIO timing markers, or
- compact numeric telemetry records queued nonblockingly.

Human-readable formatting can happen on M4 or on the PC.

## 8. Trace Capture Architecture on RP2040

### 8.1 Event capture, not continuous sampling

The probe should record changes rather than sample a waveform at a fixed high rate.

For four trace inputs, treat them as one four-bit state:

```text
0000  no marked subsystem active
0001  audio active
0011  audio + storage active
0101  audio + UI active
...
```

Each capture record represents a state transition plus time information.

Conceptually:

```c
typedef struct {
    uint32_t timestamp_ticks;
    uint8_t  state;
} trace_edge_t;
```

A later encoding may use delta timestamps to reduce size.

### 8.2 First implementation: CPU-driven proof of concept

Before writing PIO code, prove the end-to-end architecture using ordinary GPIO/IRQ handling for one low-frequency test signal.

Requirements:

- Detect both edges.
- Timestamp with a Pico hardware timer.
- Place records into a ring buffer.
- Stream records to the host.
- Demonstrate that CMSIS-DAP remains functional while trace is active.

This version is not expected to be the final timing solution. Its purpose is to validate interfaces and data flow.

### 8.3 PIO capture

Once the pipeline works, migrate trace edge detection/state observation to PIO.

PIO should:

- Monitor a contiguous pin group.
- Detect when the sampled state differs from the previous state.
- Push a compact record or state token into the RX FIFO.
- Avoid interrupting the RP2040 CPU for every edge.

The exact timestamp strategy should be evaluated experimentally. Options include:

- PIO-maintained cycle/delta counts.
- Pairing state records with an RP2040 hardware timer in DMA/CPU service code.
- A dedicated PIO counter mechanism.

Do not lock the design to a timestamp mechanism before measuring precision, overflow behavior, PIO instruction cost, and resource conflicts with the existing debugprobe PIO usage.

### 8.4 PIO resource audit is mandatory

The stock debugprobe already uses RP2040 PIO resources for debug transport. Before assigning a trace state machine, Codex must inspect the current upstream source and document:

- Which PIO block(s) are used.
- Which state machines are used.
- Which instruction-memory regions/programs are used.
- Whether programs are loaded/unloaded dynamically.
- Any assumptions about pin bases and DMA channels.

The trace implementation must coexist rather than assume unused resources.

### 8.5 DMA buffering

Once PIO capture is stable, use DMA to move PIO RX data into RAM.

Preferred design:

```text
PIO RX FIFO -> DMA -> buffer A
                     buffer B
                     ...
```

Possible implementations:

- Ping-pong buffers.
- Chained DMA channels.
- Circular buffer with producer/consumer indices.

The selected scheme should minimize CPU intervention and make overflow detectable.

Every overflow path must increment a counter that the host can query.

## 9. Timebase and Record Encoding

### 9.1 Requirements

The trace timebase should provide:

- deterministic ordering,
- sufficient resolution for audio/DSP/UI timing,
- unambiguous wrap handling,
- low per-event storage cost,
- correlation with software telemetry.

### 9.2 Start with 32-bit ticks

Use a simple 32-bit tick field initially. Choose a documented fixed frequency.

Host tools must handle wraparound correctly.

### 9.3 Consider delta encoding later

Once correctness is established, test a compact record such as:

```c
typedef struct {
    uint32_t delta_ticks;
    uint8_t  state;
} trace_delta_t;
```

If most inter-event gaps fit in a smaller integer, a variable-length encoding could eventually reduce USB bandwidth further. Do not introduce variable-length compression until raw fixed-size records are reliable and well tested.

### 9.4 Clock-domain correlation

Hardware capture timestamps originate from the Pico clock domain. Structured telemetry generated by STM32 may originate from an STM32 timer.

If both are shown on one timeline, provide explicit synchronization markers.

A simple strategy is:

1. Host tells Pico to arm.
2. Pico asserts or requests a synchronization event.
3. STM32 emits both a telemetry `SYNC` record and a trace GPIO pulse.
4. Host aligns the two streams using the matched sync event.

Do not assume independently running clocks remain perfectly aligned over long captures.

## 10. Triggered Flight Recorder

### 10.1 Motivation

Intermittent bugs are often discovered after the interesting causal history has already passed.

The probe should therefore support a circular pre-trigger history.

### 10.2 Capture states

Recommended state machine:

```text
IDLE
  |
  v
ARMED / circular capture
  |
  | trigger
  v
POST_TRIGGER
  |
  | requested post interval complete
  v
FROZEN
  |
  v
DOWNLOAD / REARM
```

### 10.3 Trigger sources

First trigger source:

- Rising edge on dedicated `TRACE_TRIGGER` input.

STM32 can pulse this on:

- audio underrun/overrun,
- unusually long SD write,
- HardFault entry,
- queue corruption,
- watchdog pre-fault warning,
- manually requested diagnostic event.

Later trigger sources may include host commands or pattern-based trace conditions.

### 10.4 Pre/post-trigger configuration

Initial reasonable target:

- 1-3 seconds of pre-trigger history if RAM/event rate permits.
- 100-500 ms post-trigger capture.

Actual capacity must be calculated from measured event rates and record size rather than assumed.

### 10.5 Failure behavior

If trace activity is too high to retain the configured history, report the effective retained duration and overflow count. Never silently pretend the requested pre-trigger window was preserved.

## 11. Normal UART Logging Architecture

The M4 should own the physical diagnostic UART.

Both cores may use a shared logging API, but M7 messages should reach M4 through a dedicated, nonblocking logging queue rather than through the same queue used for functional inter-core commands/events.

Recommended logical channels:

```text
Shared IPC
  - control/state/events        reliable/high priority
  - diagnostic log queue       best effort
```

M4 may use UART DMA to transmit console output.

If the diagnostic log queue fills:

- drop messages,
- increment `dropped_log_records`,
- periodically report the count.

Never block M7 waiting for UART capacity.

## 12. Structured Binary Telemetry

Structured telemetry is a later layer on top of the hardware timing capture.

### 12.1 Why it exists

Hardware trace can tell the host:

> The storage interval lasted 1.8 ms.

Telemetry can add:

> That interval was a 32 KiB write, queue depth was 3, and the card latency class was X.

### 12.2 Example event types

Potential events:

```text
AUDIO_BUFFER_LEVEL
AUDIO_OVERRUN
DSP_FRAME
DSP_LOAD
SD_WRITE_BEGIN
SD_WRITE_END
SD_WRITE_BYTES
IPC_QUEUE_DEPTH
IPC_DROP_COUNT
UI_FRAME
RADIO_TUNE
RADIO_BAND_CHANGE
EMF_LEVEL
MODE_CHANGE
SESSION_STATE
BATTERY_STATE
FAULT
SYNC
```

Do not attempt to define the complete event catalog before actual debugging needs emerge.

### 12.3 Target record characteristics

Telemetry records should be:

- binary,
- fixed-size where practical,
- versioned,
- endian-defined,
- no heap allocation,
- cheap to enqueue,
- safe to drop if marked best-effort.

Example concept:

```c
typedef struct {
    uint32_t timestamp;
    uint16_t type;
    uint16_t flags;
    uint32_t arg0;
    uint32_t arg1;
} spooky_telemetry_event_t;
```

Different event payload strategies may be introduced later if necessary.

## 13. Serial Framing for Structured Telemetry

If the same physical UART carries binary packets, use explicit framing.

Recommended initial candidate: **COBS + zero-byte delimiter**.

Wire form:

```text
[COBS encoded packet] 00 [COBS encoded packet] 00 ...
```

Packet contents should include at least:

```text
protocol version
packet type
sequence number
payload length
payload
checksum/CRC
```

A CRC is useful for diagnostics because UART corruption or parser bugs should be detectable rather than interpreted as valid events.

### Text vs binary modes

Early options:

1. Keep normal text logging on the existing UART and add a separate physical telemetry UART later.
2. Multiplex text and binary records through one framed protocol.
3. Make the debug UART switchable between text and telemetry modes.

For the first trace milestones, do **not** make binary telemetry a prerequisite. Hardware trace should be useful even with the UART operating exactly as it does today.

## 14. USB Architecture

### 14.1 Initial approach

Preserve the stock debugprobe USB behavior first.

The simplest trace transport that does not destabilize the existing stack should be selected after inspecting current source organization.

A likely development path is:

- CMSIS-DAP: unchanged.
- Existing CDC UART: unchanged.
- Trace: initially an additional CDC ACM interface if straightforward.

The host may then see approximately:

```text
CMSIS-DAP debug interface
COM/tty #1 - STM32 console
COM/tty #2 - Spooky Trace control/data
```

### 14.2 Later vendor bulk interface

If CDC throughput, latency, driver behavior, or framing becomes limiting, migrate the trace stream to a vendor-specific USB bulk interface.

Do not do this until measurements show a need.

### 14.3 USB descriptors and compatibility

Any USB change must be tested on the developer's actual host OS and must not break OpenOCD enumeration of CMSIS-DAP.

Maintain stable interface strings where possible so host scripts can identify the correct port/interface.

## 15. Pico Firmware Module Layout

Exact names should follow the upstream project conventions after inspection. Conceptually add modules equivalent to:

```text
src/
  ... existing debugprobe code ...

  spooky_trace/
    trace_capture.c/.h
    trace_pio.pio
    trace_dma.c/.h
    trace_buffer.c/.h
    trace_protocol.c/.h
    trace_usb.c/.h
    trace_trigger.c/.h
    trace_stats.c/.h
```

Responsibilities:

### `trace_capture`
Owns high-level start/stop/arm state and capture configuration.

### `trace_pio`
PIO program and state-machine setup for pin-state change capture.

### `trace_dma`
DMA setup, chaining, completion handling, buffer handoff.

### `trace_buffer`
Ring/ping-pong buffer ownership, overflow accounting, producer/consumer rules.

### `trace_protocol`
Stable host-facing record definitions, versioning, command parsing.

### `trace_usb`
Moves trace records to/from the selected USB interface without exposing USB details to capture code.

### `trace_trigger`
Implements ARMED -> POST_TRIGGER -> FROZEN semantics.

### `trace_stats`
Counters for dropped events, buffer high-water, triggers, USB stalls, etc.

Keep dependencies one-directional where possible. PIO/DMA capture should not know about CMSIS-DAP or application-level host commands.

## 18. Event-Bus Extension (Later)

If dedicated pins become limiting, add a small encoded event bus.

Example:

```text
EVENT0
EVENT1
EVENT2
EVENT3
STROBE
```

STM32 sets a four-bit event ID and pulses `STROBE`.

That provides 16 instantaneous event types using five wires.

This is useful for events such as:

```text
DSP_BEGIN
DSP_END
SD_BEGIN
SD_END
BAND_CHANGE
QUEUE_HIGH
BUTTON_EVENT
FAULT
```

Do not replace the dedicated duration pins with this scheme. Dedicated pins are valuable because pulse width directly represents elapsed time and they remain easy to inspect with an oscilloscope or logic analyzer.

A mature probe may support both.

## 19. Reliability and Failure Semantics

Every diagnostic path needs explicit failure behavior.

### Probe trace buffer full

- Drop oldest or newest records according to current capture mode.
- Increment an overflow counter.
- Surface overflow prominently to host.

### Host not reading fast enough

- Never block CMSIS-DAP indefinitely.
- Continue local buffering until capacity is reached.
- Drop trace data according to policy.

### Target telemetry queue full

- Drop best-effort records.
- Increment a target-side counter.
- Never block M7 audio/DSP.

### M4 failure

- Hardware trace remains observable.
- SWD remains available.
- M7 normal text logging through the M4 may be unavailable.

### M7 fault

- Fault handler should pulse trigger as early/safely as possible.
- Optionally write a minimal crash record into a known SRAM region.
- Probe freezes trace history.

### Pico trace subsystem failure

- DAP should remain operational if physically possible.
- Report trace subsystem error through trace status/LED without altering target execution.

## 20. Testing Strategy

### 20.1 Regression test rule

Every milestone that modifies the probe must rerun the baseline debugger smoke test.

Minimum baseline checks:

1. Pico enumerates correctly over USB.
2. OpenOCD discovers the CMSIS-DAP interface.
3. STM32 can be halted.
4. STM32 memory/registers can be read.
5. Firmware can be programmed.
6. Target can reset/run.
7. UART console still transmits and receives.

Trace code is not considered successful if any of the above regress.

### 20.2 Synthetic trace generator

Before relying on Spooky Box firmware, build a simple STM32 or second Pico test program that produces known patterns:

```text
TRACE0: 1 ms pulse every 10 ms
TRACE1: 250 us pulse every 3 ms
TRACE2: overlapping 2 ms bursts
TRACE3: trigger after 5 seconds
```

Use a scope/logic analyzer, if available, to compare actual pulse timing with Spooky Trace output.

### 20.3 Stress tests

Test combinations including:

- continuous OpenOCD polling while trace streams,
- active GDB stepping while target UART is busy,
- maximum expected trace event rate,
- trace USB consumer intentionally paused,
- repeated USB disconnect/reconnect,
- target reset while capture active,
- Pico reset while target continues running,
- timestamp wraparound,
- DMA buffer wrap/chaining boundaries.

### 20.4 Long-run test

Run a capture for at least several hours using a representative event rate and verify:

- no DAP failure,
- no memory leak,
- no lockup,
- correct timestamp ordering,
- expected overflow behavior,
- host reconnection behavior.

## 21. Milestones and Acceptance Criteria

### Milestone 0 - Reproducible upstream baseline

**Goal:** Establish a known-good fork and build.

Deliverables:

- Fork builds from documented commands.
- UF2 can be generated.
- H755 can be debugged over CMSIS-DAP.
- UART CDC works.
- `README-spooky.md` documents exact baseline.

Acceptance:

- No Spooky-specific code yet.
- A clean checkout can be built by following repo instructions.

---

### Milestone 1 - One-pin trace proof of concept

**Goal:** Prove complete target -> Pico -> USB -> host event path.

Implementation:

- One GPIO input.
- CPU/IRQ edge capture acceptable.
- RP2040 timer timestamp.
- Fixed-size event record.
- Simple trace output interface.
- Python decoder prints timestamp + edge/state.

Acceptance:

- Known 1 ms pulses decode correctly within documented measurement error.
- CMSIS-DAP and UART still pass baseline smoke tests.

---

### Milestone 2 - Four-pin state-change capture

**Goal:** Capture the planned Spooky Box timing lanes.

Implementation:

- GP10-GP13 contiguous state capture.
- Combined pin-state records.
- Host labels signals and reconstructs pulses.

Acceptance:

- Overlapping synthetic pulses reconstruct correctly.
- No event reordering.
- Overflow is detectable.

---

### Milestone 3 - PIO capture

**Goal:** Remove edge-rate sensitivity from normal RP2040 CPU interrupt load.

Implementation:

- Document debugprobe PIO resource usage.
- Add nonconflicting trace PIO program/state machine.
- Produce same host-facing record semantics as Milestone 2.

Acceptance:

- Timing accuracy improves or remains stable under USB/DAP load.
- CMSIS-DAP regression suite passes.

---

### Milestone 4 - DMA buffering

**Goal:** Make capture resilient to temporary CPU/USB stalls.

Implementation:

- PIO -> DMA -> RAM buffering.
- Explicit buffer ownership.
- Overflow/high-water statistics.

Acceptance:

- Trace continues correctly during intentionally induced CPU load.
- Buffer overflow is reported and recovers cleanly.

---

### Milestone 5 - Triggered flight recorder

**Goal:** Preserve history before intermittent failures.

Implementation:

- ARMED circular capture.
- Trigger input.
- Configurable post-trigger interval.
- FROZEN capture download.

Acceptance:

- Triggered file contains documented pre-trigger and post-trigger intervals within capacity limits.
- Re-arm works repeatedly without reboot.

---

### Milestone 6 - Spooky Box STM32 instrumentation

**Goal:** Use trace in the actual application.

Implementation:

- M7 audio interval marker.
- M7 storage interval marker.
- M4 UI interval marker.
- fault/diagnostic trigger marker.
- compile-time enable/disable.

Acceptance:

- Trace overhead on M7 is measured and documented.
- Audio behavior does not measurably regress under normal instrumentation.
- Timeline can show real audio/storage/UI overlap.

---

### Milestone 7 - Structured telemetry

**Goal:** Add semantic context to timing traces.

Implementation:

- versioned telemetry event definitions,
- nonblocking target queues,
- framing/CRC,
- host decoder,
- sync event for clock alignment.

Acceptance:

- Hardware pulse and corresponding software `SYNC` event align in host view.
- Full telemetry buffers never block M7.

---

### Milestone 8 - Useful visualization

**Goal:** Make traces fast to interpret.

Implementation:

- Static timeline plot first.
- Event markers.
- zoom/window selection in CLI or generated output.
- capture metadata.

Acceptance:

- A developer can answer "what overlapped the underrun?" from one capture without manually parsing raw records.

## 22. Repository Strategy

There are two reasonable repo arrangements.

### Option A - Fork `raspberrypi/debugprobe`

Recommended initially.

```text
spooky-debugprobe/
  <upstream debugprobe tree>
  docs/
    spooky-trace.md
  tools/
    spookytrace/
```

Advantages:

- easiest upstream comparison,
- simplest firmware build,
- Codex can inspect the whole implementation in one repository.

### Option B - Separate host tooling repository

If the Python tooling grows significantly, split later:

```text
spooky-debugprobe       firmware fork
spooky-trace-tools      host capture/viewer
```

Do not split prematurely.

## 23. Codex / Agent Working Rules

This project is well suited to agent-assisted implementation, but low-level debug firmware is also an area where broad refactors can create subtle regressions. Give agents narrow work packages and explicit validation criteria.

### 23.1 Agent rule: inspect before editing

For every unfamiliar subsystem, first ask Codex to produce a short source audit before modifying anything.

For example:

> Inspect the current `raspberrypi/debugprobe` tree and identify the USB stack, CMSIS-DAP entry points, UART bridge implementation, RP2040 PIO programs/state-machine usage, DMA-channel usage, multicore/task model, and board-specific Pico configuration. Do not edit files yet. Return a proposed integration seam for an independent trace subsystem and list resource conflicts or uncertainties.

This prevents an agent from designing against assumptions from an older debugprobe version.

### 23.2 Agent rule: preserve upstream behavior

Every implementation prompt should include:

> Do not refactor or rewrite existing CMSIS-DAP/SWD code unless the requested feature cannot be implemented otherwise. Treat existing debugprobe functionality as a regression-sensitive dependency.

### 23.3 Agent rule: one milestone per task

Do not prompt:

> Implement Spooky Trace.

Prompt:

> Implement Milestone 1 only: one GPIO edge input, timestamped records, a bounded buffer, and a simple host decoder. Do not add PIO, DMA, trigger capture, or binary STM32 telemetry yet.

This produces reviewable commits and makes hardware validation practical.

### 23.4 Agent rule: require a resource ledger

For RP2040 changes, maintain a document/table containing:

```text
PIO block / state machines
PIO instruction memory
DMA channels
hardware alarms/timers
GPIO ownership
USB interfaces/endpoints
RP2040 core/task ownership
RAM buffers and approximate sizes
```

Codex should update this ledger whenever it allocates a resource.

### 23.5 Agent rule: require explicit overflow behavior

For every queue, ring buffer, DMA buffer, or USB transfer path, the implementation must document:

- who owns producer index,
- who owns consumer index,
- whether operations are ISR-safe,
- what happens when full,
- how overflow is counted,
- whether any producer can block.

No implicit "should be fast enough" assumptions.

### 23.6 Agent rule: hardware-facing assumptions become comments/docs

When Codex assumes a pin mapping, voltage, timer frequency, UART baud, PIO clock, USB endpoint size, etc., require it to place the assumption in a board config or documentation rather than burying a magic value in code.

### 23.7 Agent rule: tests before optimization

Ask for host-side unit tests for:

- packet encode/decode,
- timestamp wrap,
- COBS framing if used,
- CRC rejection,
- pin-state reconstruction,
- trigger-state transitions,
- capture-file parsing.

These can be fully developed without hardware and are excellent tasks for autonomous agents.

## 24. Suggested Codex Work Packages

### Work Package F - DMA buffering

**Prompt:**

### Work Package G - Triggered recorder

**Prompt:**

## 26. Recommended Human/Agent Development Loop

For each milestone:

```text
1. Human defines narrow milestone
2. Codex audits relevant code/resources
3. Codex proposes change
4. Codex implements + unit tests
5. Codex builds firmware/tools
6. Human flashes hardware
7. Human runs prescribed smoke/stress test
8. Human supplies observations/logs back to Codex
9. Codex fixes issues
10. Commit/tag known-good milestone
```

The important pattern is that Codex can do most source work autonomously, while the human remains the oracle for physical timing and electrical behavior.

## 27. Coding Conventions Worth Establishing Early

- No dynamic allocation in trace capture hot paths.
- Fixed-width integer types in wire formats.
- Explicit little-endian encoding unless a different wire order is deliberately chosen.
- Static assertions for packed/wire structure sizes where appropriate.
- Protocol version in every capture/session header.
- No direct USB calls from PIO/DMA completion code if they can block.
- No target dependency on trace probe presence.
- Board pin mappings centralized.
- All diagnostic drops/overflows measurable.
- No silent data truncation.
- Keep test/synthetic generators available in production source behind build flags rather than deleting them after bring-up.

## 28. Open Technical Questions

These should be answered by source audit and experiments rather than guessed up front.

1. Which PIO state machines and program memory are safely available in the current upstream debugprobe build?
2. What timestamp strategy gives the best tradeoff between precision, PIO resources, DMA simplicity, and record size?
3. Does the existing debugprobe USB stack make a second CDC ACM interface straightforward, or is a different trace transport cleaner?
4. What sustained trace event rate can the Pico stream without affecting CMSIS-DAP responsiveness?
5. How much Pico RAM can reasonably be dedicated to pre-trigger history?
6. What real trace event rate does Spooky Box generate with audio/storage/UI instrumentation?
7. Is UART telemetry worth multiplexing with text logging, or should a separate transport eventually be used?
8. How much drift exists between STM32 and Pico clocks over a typical capture, and how often are sync points needed?
9. Does the final custom Spooky Box PCB need four, six, or more dedicated trace pins?
10. Would exporting to an existing viewer format be more useful than maintaining a custom visualizer?

Keep this list alive. Convert questions into measured answers as prototypes mature.

## 29. Definition of a Successful First Version

Spooky Probe does **not** need a polished GUI or sophisticated event protocol to justify itself.

The project has crossed the "useful" threshold when a developer can:

1. Plug one Pico into the PC and Spooky Box.
2. Debug the H755 through CMSIS-DAP.
3. Read normal M7/M4 logs through the UART bridge.
4. Arm hardware trace capture.
5. Reproduce an intermittent audio/storage/UI problem.
6. Retrieve a timeline showing which marked subsystems overlapped around the trigger.

If that workflow reliably answers a real debugging question faster than ordinary logging, the project is already successful.

Everything after that is refinement.

## 30. Long-Term Vision

A mature Spooky Probe could become a standard development companion for every SpookyTronics device:

```text
                    SPOOKY PROBE

USB <----------------------------------------> PC
 |
 +-- CMSIS-DAP ---------- SWD ----------> target
 |
 +-- CDC console -------- UART ---------> target
 |
 +-- Spooky Trace ------- GPIO/events --> target
 |
 +-- trigger/history/telemetry
```

That gives Spooky Box a debugging interface designed around its actual architecture rather than relying solely on generic debugger behavior.

The key value is independence: when timing-sensitive firmware behaves badly, the trace probe is not another task running inside the system under test. It is watching from outside.

For a dual-core audio/DSP instrument, that can become one of the most useful tools on the bench.
